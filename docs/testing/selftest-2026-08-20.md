## Bugs found and fixed this session

### 1. Claude Code CLI 2.1.237 silently coerces unrecognized `--model` values

**Symptom:** Groq and OpenCode both 404'd/failed with a request that had `"model":
"claude-sonnet-5"` even though the launch env passed `--model openai/gpt-oss-120b` /
`--model mimo-v2.5`.

**Root cause:** confirmed via debug logging at the proxy's HTTP ingress (before any of our own
code touches the request) — the CLI itself was substituting `claude-sonnet-5` for *any* `--model`
value it doesn't recognize as one of the account's allowed Anthropic models, including
`claude-opus-5` (a real, valid Claude alias — debug log: `"Fast mode unavailable: Opus 5 is not
in your organization's allowed models"`). This broke every provider that relies on `--model` to
carry a non-Anthropic model id through to a local translation proxy.

**Fix:** [`AnthropicCompatProxy`](../../app/src/TokenOptimizer.Providers/Compat/AnthropicCompatProxy.cs)
now takes a `forceModel` parameter and re-injects the real target model into the request body
before forwarding upstream, ignoring whatever the CLI put there. `GroqAdapter` and
`ModelProbeService.ProbeGroqAsync`/`ProbeOpenCodeAsync` pass the intended model through.
Commit: `fix: pin outgoing model id for proxied Groq/OpenCode sessions`.

**Scope note:** `UnifiedModelRouter` (the multi-model-ticked launch path in
`MainViewModel.LaunchTickedModelsAsync`) has the same exposure and was **not** fixed — it routes
by matching the incoming (CLI-coerced) model field against a per-model route table, so if the CLI
collapses every non-Anthropic model choice to the same default id, the router can no longer tell
which of several ticked non-Claude models the user's `/model` picker actually selected. Fixing
that requires a different mechanism (e.g. one proxy port per model, or an out-of-band model
signal) and is out of scope for this pass. Filed as a known limitation, not fixed.

### 2. OpenCode passthrough used the wrong auth header

**Symptom:** Every OpenCode probe returned `"Probe timed out."` after ~120s, which looked
identical to a slow/dead gateway.

**Root cause:** `opencode.ai/zen/go` speaks the Anthropic Messages API, which authenticates via
`x-api-key` (+ `anthropic-version`), not an OAuth-style `Authorization: Bearer` token. The
passthrough proxy sent `Bearer`, opencode.ai returned `401`, and the Claude Code CLI silently
retried ~8 times over its ~120s budget before giving up — so the failure surfaced as a plain
timeout with zero indication it was an auth problem. Confirmed via `~/.local/share/opencode/auth.json`,
which stores the key as `"type": "api"` (not OAuth), and via debug logging showing the retry
loop of `401` responses.

**Fix:** proxy now sends `x-api-key` + `anthropic-version: 2023-06-01`, and relays the real
upstream error body on failure instead of a generic message. Commit:
`fix: OpenCode passthrough uses x-api-key, not Authorization: Bearer`.

**Result after fix:** the credential now authenticates (single request, no retry storm) and the
correct model id (`mimo-v2.5`, not the CLI-coerced default) reaches opencode.ai — proving both
fixes above work. The remaining failure is external, see below.

## External / environmental failures (not fixed, evidence attached)

### Groq: account TPM tier too small for the matrix

Every Groq probe fails with `"Model returned empty response."` — no error text, because the CLI
swallows non-200 proxy responses silently in `-p` mode (a CLI behavior, not something this
codebase controls). Debug logging at the proxy showed the real upstream response:

```
429 {"error":{"message":"Rate limit reached for model `openai/gpt-oss-120b` in organization
`org_01ky1yv8c4ey7avfxv3ecffr4k` service tier `on_demand` on tokens per minute (TPM): Limit 8000,
Used 4268, Requested 7323. ..."}}
```

One Claude Code request costs ~7,300 tokens against this account's 8,000 TPM budget — almost
entirely the CLI's own system prompt and full tool-schema payload (Bash, Read, Edit, etc.), not
the 1-token probe prompt. Five back-to-back probes structurally cannot fit in one rolling minute
on this tier regardless of code correctness. **The model-routing fix (bug #1) is verified correct**
— a clean single probe run got a real `429` from Groq's own infra (not a 404 "model not found"),
proving the request now reaches Groq with the right model id and a valid key. This is an account
tier limit, not a code bug. A real single-model launch (not a 5-in-a-row batch probe) would not
hit this in normal use.

### OpenCode: gateway has a server-side tool-schema bug

With auth and model-routing both fixed, `mimo-v2.5` still returns:

```
400 {"error":{"type":"server_error","message":"Error from provider (Console Go): Upstream
request failed: [400] Provider returned error"}}
```

Testing a second model (`glm-5`) through the same fixed path surfaced a much more specific error
from opencode.ai's own backend:

```
400 {"error":{"type":"invalid_request_error","message":"Error from provider (Console Go):
Upstream request failed: [invalid_parameter_error] 'name' is a required property -
'tools.0.function'"}}
```

Claude Code always sends its full tool array in Anthropic's native shape
(`tools: [{name, description, input_schema}]`). This error means opencode.ai's own gateway is
internally re-shaping that into something resembling OpenAI's nested `tools[].function.name`
format for at least this provider, and that internal conversion is dropping/mis-mapping the tool
name — a bug in opencode.ai's own backend, not in this proxy (which forwards the Anthropic-shaped
body verbatim aside from the model-id override). Previously diagnosed (2026-08-20) as a "500
gateway outage" — that diagnosis was itself confounded by the CLI model-coercion bug (#1): the
gateway was being sent the wrong model id the whole time. With that fixed, the real, narrower
issue is this tool-schema translation bug on opencode.ai's side.

### Unsloth: local hardware cannot hold both cached models at once

Both local GGUF models load fine individually (confirmed working in a prior session run: "KAT-Coder
Worked Successfully"), but the studio cannot hold both loaded at once. Switching from the 21GB
`mudler/KAT-Coder-V2.5-Dev-APEX-GGUF` to the 13GB `unsloth/Qwen3.8-27B-GGUF` fails allocation:

```
E ggml_backend_cpu_buffer_type_alloc_buffer: failed to allocate buffer of size 7516192768
E alloc_tensor_range: failed to allocate CPU buffer of size 7516192768
E llama_init_from_model: failed to initialize the context: failed to allocate buffer for rs cache
```

(A separate run of the same matrix hit the identical failure on the CUDA allocator instead of
CPU, depending on which resource filled up first — same underlying cause.) The second model in
the matrix (`KAT-Coder`, already the one loaded from the first model's failed switch-away) then
times out at the probe's 120s ceiling — consistent with the documented 1-3 minute cold-load
latency for a 21GB model exceeding the probe window, not a code defect. `LlamaCppAdapter.cs:224`
has the same underlying assumption (studio must already be running) that was worked around
manually for this session — see the plan's "known limitation" note; not refactored here per the
plan's explicit scope boundary.
